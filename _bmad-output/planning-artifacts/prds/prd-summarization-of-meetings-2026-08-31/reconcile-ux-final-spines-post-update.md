## Найденные расхождения

### F-1 — Автоматические Теги превращены из обязательного поведения в опциональное

**Уровень:** высокий для цели этого обновления.

Подтверждённый источник говорит, что тематические Теги должны проставляться автоматически и допускать ручное изменение (`UX .memlog.md`, строка 8), а финальный UX-контракт уточняет: auto-tags появляются после успешного Саммари и редактируемы владельцем (`EXPERIENCE.md`, строка 114; Flow 5, строки 241–245).

Текущий PRD ослабляет это решение:

- глоссарий называет Тег «предложенным приложением» (`prd.md`, строка 118);
- FR-22 говорит, что приложение «может назначить» тематические Теги (`prd.md`, строка 386).

В результате реализация без автоматического назначения Тегов формально удовлетворит PRD, хотя не удовлетворит подтверждённому UX-решению. Остальные правила Тегов — единый редактируемый набор, появление только после успешного Саммари, provenance только в edit mode и фильтрация — перенесены корректно.

### F-2 — Не перенесено поведение поиска по номеру при отсутствии совпадения

**Уровень:** средний.

Финальный UX-контракт задаёт конкретный failure state: при отсутствии exact/prefix совпадения по номеру нужно сохранить запрос, предложить очистить фильтры и явно сообщить, что поле использует структурированное локальное сопоставление; semantic/fuzzy match не выдумывается (`EXPERIENCE.md`, строки 212–218; State Patterns, строка 132).

Текущий FR-19 фиксирует запрет подмены результата fuzzy/semantic совпадением и сохранение контекста при открытии/возврате (`prd.md`, строки 353–354), но не требует:

- сохранить запрос именно в no-hit state;
- дать действие очистки фильтров;
- назвать применённый structured local matching пользователю.

Отдельный structured exact/prefix механизм и его архитектурная передача при этом отражены правильно (`prd.md`, строки 345–354; `addendum.md`, строка 33).

### F-3 — Добавлены неподтверждённые количественные критерии выпуска и производительности

**Уровень:** средний; требуют отдельного решения владельца продукта либо удаления/маркировки как assumptions.

Финальные UX-источники подтверждают сами возможности, но не следующие числа:

- не менее двух прямых аудиофайлов и минимум один некорректный аудиофайл в корпусе из десяти (`prd.md`, строка 98);
- точность позиционирования плеера до 2 секунд (`prd.md`, строка 99);
- поиск Встречи по точному номеру Внешней задачи менее чем за 2 минуты как часть SM-3 (`prd.md`, строка 82); в UX порог «до двух минут» относится к проверке договорённости по источнику, а не к архивному поиску (`EXPERIENCE.md`, строки 220–225);
- exact/prefix-поиск и фильтрация по 1 000 Встречам не более чем за 2 секунды (`prd.md`, строка 436); исходный PRD имел 2-секундную цель для открытия библиотеки/переходов, но финальные UX-спайны не подтверждали расширение этого порога на новые операции.

Это не противоречит UX, но создаёт новые обязательства выпуска, которых пользователь не подтверждал как часть семи решений. Само требование протестировать прямое аудио, плеер и structured task-number search разумно; неподтверждёнными являются конкретные количества и пороги.

## Проверенные совпадения без дополнительных gaps

- **Прямой audio import:** PRD корректно отличает прямой импорт от извлечения аудиодорожки, сохраняет заполненную форму при preflight failure, не создаёт Meeting/job и не выдумывает ещё не утверждённые форматы (`prd.md`, строки 134–143, 230–238, 454; UX `.memlog.md`, строка 14; `EXPERIENCE.md`, строки 106, 133, 198–208, 317).
- **Плеер:** поведенческая часть соответствует `EXPERIENCE.md`, строки 62–66, 109, 112–113, 145–152, 161, 171 и 222–227. Реализационные детали Ant Design/browser-native controls из `DESIGN.md` не превращены в FR, что корректно.
- **Retention:** PRD сохраняет Встречу и Исходную запись до явного удаления, не вводит автоматический срок, сохраняет текст после media-only deletion и не маскирует partial deletion (`prd.md`, строки 145–176; UX `.memlog.md`, строка 12; `EXPERIENCE.md`, строки 28, 109, 119, 161, 259–266).
- **Участники:** PRD полностью сохраняет ключевую границу participants ≠ speakers/users/access и delete-detach behavior (`prd.md`, строки 119–120, 253–262, 391–400; UX `.memlog.md`, строки 17–18; `EXPERIENCE.md`, строки 41, 105, 115, 119, 136, 241–247).
- **Внешняя задача:** FR-24 и addendum не превращают сохранение URL/номера в интеграцию, не обещают чтение атрибутов или синхронизацию (`prd.md`, строки 121, 402–411; `addendum.md`, строки 10–11; UX `.memlog.md`, строки 8, 15, 26; `EXPERIENCE.md`, строки 30, 104–105, 116, 212–218, 241–247).
- **Структурированный поиск:** exact/prefix поле не смешано с FTS/fuzzy/semantic search; архитектурный механизм корректно оставлен в addendum (`prd.md`, строки 156–164 и 345–354; `addendum.md`, строка 33; `EXPERIENCE.md`, строки 30, 37, 104–105, 116, 132, 212–218, 243–247, 318).

## Addendum verdict

По семи решениям `addendum.md` не содержит самостоятельных противоречий или пропусков, требующих исправления отдельно от PRD:

- direct audio — строки 7 и 19;
- локальное хранение Тегов, Участников и Внешней задачи — строка 10;
- URL/номер без tracker API — строка 11;
- хранение без автоматического срока и media-only delete — строка 23;
- structured exact/prefix architecture follow-up — строка 33.

Реализационных обещаний о конкретных аудиоформатах, task-number parser или UI-компонентах addendum не добавляет.
